# ISO/IEC 42001 orientation

> **This tool does not certify, assess or guarantee compliance with ISO/IEC
> 42001.** ISO/IEC 42001:2023 specifies requirements for establishing,
> implementing, maintaining and continually improving an **AI Management System
> (AIMS)**. It does not prescribe a tool, a registry schema, or an inventory
> format. This project produces *inputs* — an evidence-backed AI inventory — that
> an organization can use within its AIMS, nothing more.

## Why this mapping exists

Clause 7.5 (documented information) and the Annex A controls around AI system
life cycle, impact assessment and operation all depend on knowing **what AI
systems exist, who owns them, what they do, and whether they are actually used**.
Organizations frequently cannot answer these questions, because AI usage enters
an account through many doors (managed services, SDK calls, third-party
applications, ad-hoc notebooks).

The discovery agent narrows that gap by producing a structured, defensible
record set. The governance module then reports, honestly, **which fields needed
for AIMS documentation are missing**.

## Field → AIMS documented-information mapping

Each governance field maps to the kind of documented information an AIMS
typically expects. The tool reports **gaps** (missing fields); it never asserts
that a control is satisfied.

| Registry field | AIMS documented-information expectation |
|---|---|
| `ai_system_name` | Identified AI system (cl. 8.1 life cycle; 8.2 impact-assessment inputs) |
| `intended_purpose` | Documented intended purpose and limitations (cl. 8.2.2; 8.3.2) |
| `system_owner` | Assigned accountability / ownership (cl. 5.3; 6.1.2) |
| `business_owner` | Business accountability (cl. 5.3) |
| `technical_owner` | Technical responsibility for operation (cl. 8.5.1) |
| `intended_users` | Affected parties / context of use (cl. 6.1.2.2; 8.2.2) |
| `data_categories` | Data / information needs (cl. 8.3.3; 8.2.2) |
| `data_classification` | Information-security controls over data (cl. 6.1.2.3; Annex A) |
| `personal_data_involved` | Personal-data considerations (cl. 6.1.2.2; 8.2.2) |
| `human_oversight` | Human oversight measures (cl. 8.2.2 c; 8.5.2) |
| `risk_assessment_status` | Impact / risk assessment status (cl. 8.2) |
| `known_risks_and_mitigations` | Identified risks and treatment (cl. 6.1.2; 8.2.4) |
| `guardrails_or_safety_controls` | Implemented operational controls (cl. 8.5) |
| `monitoring_arrangements` | Monitoring / behaviour evaluation (cl. 8.5.3; 9.1) |
| `deployment_environment` | Deployment context (cl. 8.3; 8.5.1) |
| `lifecycle_stage` | Life-cycle stage documentation (cl. 8.1; 8.3; 8.5) |

The mapping text lives in `src/governance.py::FIELD_AIMS_MAPPING` and the
machine-readable output is `reports/governance_gaps.json`.

## How discovery supports (but does not replace) AIMS activities

| AIMS-relevant activity | How the agent helps | What it does **not** do |
|---|---|---|
| Maintain an AI system inventory | Produces a deduplicated, stable-id registry across services and Regions | Decide which systems are in scope for the AIMS |
| Determine AI system applicability | Distinguishes catalogue availability from account resources and evidenced activity | Judge whether a resource constitutes a "high-risk" or in-scope AI system |
| Impact assessment inputs | Surfaces purpose/owner/data/personal-data fields and flags them missing | Perform the impact assessment or risk scoring |
| Life-cycle & change control | Captures creation/modification times, statuses, and creator from CloudTrail management events | Approve, gate or block changes |
| Monitoring & evaluation | Reports invocation activity evidence where available | Guarantee completeness of monitoring; data events must be enabled by the operator |
| Incident/evidence handling | Stores sanitised, metadata-only CloudTrail evidence with limitations | Replace a SIEM or an incident-management process |

## Ethical and accuracy posture

* **No overclaiming.** A model listed in the catalogue is `UNKNOWN`, never an
  organizational AI system. A tagged but unobserved resource is
  `POTENTIAL_AI_USAGE` with low confidence.
* **Evidence before assertion.** Only CloudTrail invocation evidence yields
  `CONFIRMED_AI_ACTIVITY`, and even then failed-only invocations are marked
  `configured_but_unverified`.
* **Explicit limitations.** Every non-confirmed record carries
  `evidence_limitations`, and the report always states that absence of events is
  not proof of non-use.
* **Human in the loop.** Records default to `human_review_status="pending"` and
  carry `follow_up_actions`; the tool never marks a system as reviewed or
  approved.
* **No compliance claim.** Every report includes: *"This report supports AI
  inventory/governance activities relevant to ISO/IEC 42001 but does not assert
  compliance or certification."*

## Governance gap output

`reports/governance_gaps.json` contains, for each non-catalogue record:

```json
{
  "record_id": "air-…",
  "resource_name": "…",
  "classification": "CONFIRMED_AI_ACTIVITY",
  "priority": "high",
  "human_review_status": "pending",
  "missing_fields": ["system_owner", "intended_purpose", "data_categories"],
  "missing_descriptions": [
    {"field": "system_owner",
     "label": "System owner",
     "aims_reference": "Assigned accountability/ownership (cl. 5.3 …)"}
  ],
  "follow_up_actions": ["…"]
}
```

Priority is derived from classification: `CONFIRMED_AI_ACTIVITY` → `high`;
`CONFIGURED_AI_RESOURCE` / `POTENTIAL_AI_USAGE` / `INACTIVE_OR_STALE` →
`medium`; catalogue/`UNKNOWN` → excluded from per-record gaps (counted
separately). Catalogue records are excluded because they are not organizational
AI systems.
